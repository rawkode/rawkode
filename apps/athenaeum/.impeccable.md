# Athenaeum — design context

## Audience
David (Rawkode) — a single power user for the primary case, with multi-vault sharing to a small number of collaborators as a secondary case. Not a public product; an all-day personal workspace.

## Product framing — "Centered on daily notes and Supertags" (David, verbatim, 2026-08-22)

> "Cloudflare OS is almost perfect, but I need our version to be centered around daily notes and
> Supertags."

Athenaeum keeps Cloudflare OS's shell architecture (persistent sidebar, docked chat, routed main
column — the "Confident command-center" direction below) but the daily note and Supertags are the
**center** of the product experience, not a sidebar entry among co-equal sections. The daily note
is home (`/notes`, labeled "Today" in the nav — the first, default route). Supertags — Tana-style
typed tags that declare fields and inherit them through a multi-parent DAG, per Enchiridion's
original design ("Supertags provide types and inherited predicates",
`apps/enchiridion/Documentation/GraphDataModel.md`) — are the organizing primitive: applying one
inline while writing (`#Person`) is a first-class writing action, not a side trip to an admin
screen, and every tag has its own schema-administration home (`/supertags`, second in the nav).

Everything else — agent chat, Apps, calendar, bookmarks, meetings, workouts, sharing, the read-only
`/graph` browse view — orbits those two. It does not disappear and does not get worse, but it is
not designed as a parallel, equally-weighted section: new features should default to *strengthening
the daily-note-plus-Supertags core* (e.g. surfacing a note's tags/fields prominently next to its
prose, letting a tag's fields be extended without leaving the flow of typing) rather than growing
another top-level peer section. Concrete implementation of this pass:
`docs/supertag-centering-decisions.md`.

## Use cases
Daily note-taking (Automerge-synced prose) with inline Supertag application and field editing,
Supertag schema administration (create tags, set parents, declare fields), browsing a typed
knowledge graph (tags/facts/edges/views) as a secondary read-only tool, calendar-merged day view,
bookmarks capture, meeting transcript review, workout review, vault sharing/collaborator
management, and conversing with an in-app agent that can propose reviewable edits to the graph.

## Tone / aesthetic direction — "Confident command-center"
Chosen 2026-08-21, explicitly requested to take structural/tonal inspiration from Cloudflare OS's workshop-frontend (chat-first shell, persistent sidebar, docked chat) — **without** reusing Cloudflare's actual `@cloudflare/kumo` component library or branding, to avoid any implied Cloudflare affiliation. Athenaeum gets its own visual identity within this structural pattern.

- Dark charcoal ground (not pure black), warm off-white text (not pure white). Tint neutrals toward the accent hue.
- One accent hue, used sparingly for state/action/agent-activity — never decoratively, never gradient-text.
- A distinctive display face for headings (not Inter/Roboto/system-default); a precise mono-adjacent (not literal monospace) face for data-dense areas (tables, graph views, ids).
- Persistent sidebar: vault switcher + section navigation, quiet, not competing with content.
- Chat panel: docked right, always reachable, never a modal.
- Tight spacing in data-dense views (tables/lists); generous spacing around prose (the daily note gets room to breathe).
- Routed views, not one long stacked page — the Phase 0-7 build produced a single-page test harness (still literally labeled "PHASE 0: NODES ROUND TRIP" in places); that scaffolding is being replaced, not styled in place.

## Constraints
- React 19 + Vite web app (`apps/athenaeum/packages/web`), Effect-based data layer already established (`useEffectQuery`/`useEffectSubscription` over a module-scoped `ManagedRuntime`) — keep that data layer, this is a shell/visual redesign, not a data-layer rewrite.
- No router currently exists in the web app; one is being added as part of this pass.
- Real backend (`packages/backend`) is unchanged by this pass — every view must keep working against the real RPC surface proven across Phases 0-7.
