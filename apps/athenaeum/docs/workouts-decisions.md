# Workouts — HealthKit import as typed graph pages: architecture decisions

Status: Phase 7 workout-import stage, complete. Resolves the plan's Context-section feature
description ("Workouts — HealthKit import as typed graph pages (Workout/Strength/Cardio/Exercise/
Set supertags)... even fitness data lives in the same typed knowledge graph") and the Phase 7
phasing bullet ("HealthKit import as typed graph pages, proves graph generality, no new
mechanism"). Scope, per this stage's hard constraints: workout **import only** — no additional
gatekeepers beyond the Phase 5 Google Calendar one (already proven, further ones are template
repetition per the plan), no blueprint/template sharing (explicitly "added only if actually
wanted," not requested here).

This document is organized as the task's two numbered decision sections, then a summary of what
was and wasn't verified live, then the concrete schema/interface the next stage builds against.

## 1. HealthKit → graph data-model mapping

### 1.1 Supertags: a parallel `WORKOUT_TAGS` constant, seeded lazily per-workspace — NOT added to `BASE_TAGS`

**Decision: six fixed, immutable (`builtin: true`) tags — `Workout`, `Strength Workout`,
`Cardio Workout`, `Strength Exercise`, `Strength Set`, `Cardio Split` — held in a new
`WORKOUT_TAGS`/`WorkoutTagIds` constant (`packages/domain/src/workout.ts`), seeded idempotently
into a workspace's `tags` collection the first time that workspace imports a workout
(`workouts-service-live.ts#ensureWorkoutTagsSeeded`, mirroring `seed-base-tags.ts`'s own
idempotency discipline), NOT merged into `tag.ts`'s existing `BASE_TAGS` array.**

Two options were on the table (the task's own framing): (a) non-builtin tags created per-workspace via
the ordinary `createTag` RPC the first time a workout is imported, or (b) promote the six tags
into the fixed, ship-with-every-workspace `BASE_TAGS` set. Neither was taken as-is; the actual decision
is a third option that keeps what's right about each:

- **Why not (a), plain non-builtin tags**: `GraphService.createTag` (`graph-service-live.ts`)
  always mints `builtin: false` — a normal user-owned tag the user can rename or delete at will.
  Enchiridion's own precedent for this *exact* tag set — `WorkoutModule.manifest`
  (`apps/enchiridion/Sources/EnchiridionCore/WorkoutModule.swift`) — marks every one of these six
  supertags `isBuiltIn: true` specifically because the import pipeline references them by a fixed
  id it must be able to trust never gets renamed out from under it (`createEdge`,
  graph-service-live.ts, fails with `RelationDefinitionNotFound`/`TagNotFound` the moment a
  referenced id stops resolving). A deletable/renamable tag the import mechanism silently depends
  on is a real footgun this codebase doesn't accept anywhere else (see `tag.ts`'s own header
  comment on why `BASE_TAGS` are immutable in the first place).
- **Why not (b), merged into `BASE_TAGS`**: that constant is a closed, cross-language-tested
  contract. `packages/domain/src/tag.test.ts#"has exactly 8 Base Tags"`,
  `packages/backend/test/graph-service.test.ts`, and the Swift↔TS fixture round trip
  (`native/AthenaeumDomain/Tests/AthenaeumDomainTests/EntityDecodingTests.swift
  #testBaseTagsFixtureMatchesPackageConstant`, generated by
  `native/AthenaeumDomain/scripts/generate-fixtures.ts`) all assert exactly 8 rows, by name, in
  order. Widening that to 14 breaks a real, currently-green, currently-tested invariant for a
  feature most workspaces will never touch — and unconditionally seeding 6 more rows into *every*
  workspace at construction (`ensureBaseTagsSeeded`'s own call site, `workspace-durable-object.ts`
  constructor) means a user with zero interest in fitness tracking carries `Cardio Split` forever.
  The plan's own prose also keeps these two concerns in separate sentences (Base Tags are
  enumerated once, "Person, Organization, Company, Event, Place, Area, Project, Task"; Workouts
  are introduced later, as a phase-7 feature, not amended into that list).
- **The actual decision**: a parallel constant (`WORKOUT_TAGS`), same "immutable, `builtin: true`,
  ship with the application" shape `BASE_TAGS` itself uses, but seeded **lazily** — only the first
  time a workspace's `WorkoutsService.importWorkout` actually runs (`workout-seed.ts
  #ensureWorkoutTagsSeeded`, idempotent: checks existing tag ids before writing, same pattern
  `seed-base-tags.ts#ensureBaseTagsSeeded` already established, extended to also seed the three
  fixed `RelationDefinition`s below). Proven idempotent for real:
  `packages/backend/test/workouts.test.ts#"seeds the 6 workout tags + 3 relation definitions
  exactly once per workspace, idempotently"` — imports a strength workout then a cardio workout into
  the same fresh workspace and asserts the tag count goes 8 → 14 → 14 (no duplicate seeding on the
  second import).

Tag DAG shape (`packages/domain/src/workout.ts`):

```
Workout                              (root, no parent — same "roots of the DAG" status BASE_TAGS' own tags have)
├── Strength Workout   (parentIds: [Workout])
└── Cardio Workout     (parentIds: [Workout])
Strength Exercise                    (no parent — never itself queried via hasTag(Workout))
Strength Set                         (no parent)
Cardio Split                         (no parent)
```

A node tagged `Strength Workout` is transitively `Workout` via `tagClosure`/`graph_tag_closure`
(`tag-closure.ts`) — `hasTag(Workout)` finds every workout regardless of kind. This is a real
divergence from Enchiridion's own `createWorkoutPage`, which explicitly assigns *every*
field-owning supertag to a node (`for owner in Set(properties.keys.map(\.supertagID)) where owner
!= tag { addSupertag(owner) }`) — necessary there because Enchiridion ties each field to its
*exact* declaring supertag. Athenaeum's `Fact` rows (`fact.ts`) carry no such tag-ownership
constraint (a `Fact` is a free `(nodeId, predicateId, value)` triple, unconnected to which tag "owns"
`predicateId`), so a single leaf-tag assignment per node is correct and sufficient here — one real,
checked simplification over the reference design, not an oversight.

Fixed nil-pattern-UUID id scheme, matching `tag.ts`'s own scheme for `BASE_TAGS` exactly (see that
file's header comment for the full "why nil-pattern UUIDs, not slugs or random UUIDs" reasoning) —
`WorkoutTagIds.Workout = 00000000-0000-0000-0000-000000000101`, `.StrengthWorkout = ...102`, and
so on through `.CardioSplit = ...106`, deliberately in a `...1NN` range disjoint from `BaseTagIds`'
`...000N` range so the two constants can never collide even if either grows.

### 1.2 Relations: three fixed `one-to-many` `RelationDefinition`s, same seeding mechanism

`packages/domain/src/workout.ts`'s `WORKOUT_RELATION_DEFINITIONS` (ids `WorkoutRelationIds
.WorkoutExercises` / `.ExerciseSets` / `.WorkoutSplits`, range `...111`–`...113`), mirroring
Enchiridion's own `WorkoutModule.Relation` one-for-one:

| Relation | Source tag | Target tag | Cardinality | Forward name |
|---|---|---|---|---|
| `workoutExercises` | Strength Workout | Strength Exercise | one-to-many | `exercises` |
| `exerciseSets` | Strength Exercise | Strength Set | one-to-many | `sets` |
| `workoutSplits` | Cardio Workout | Cardio Split | one-to-many | `splits` |

Seeded the same lazy, idempotent way as the tags (same function, same test). `createEdge`
(`graph-service-live.ts`) requires the referenced `RelationDefinition` to already exist by id —
exactly why these need fixed, known ids rather than `GraphService.createRelationDefinition`'s own
random-id-minting path (which is for user-defined relations, not this pipeline's own fixed
vocabulary).

### 1.3 Fact predicates

`WorkoutFactPredicate` (`workout.ts`) — plain kebab-case strings, this codebase's established
`Fact.predicateId` convention (`fact.ts`'s own doc comment; `AddFactInput.json`'s fixture uses
`"status"`). Deliberately reuses Enchiridion's own `WorkoutModule` field-id vocabulary almost
verbatim (`started-at`, `duration-seconds`, `average-heart-rate`, …) — a validated, shipped
vocabulary for this exact problem, not reinvented for its own sake.

Root (`Workout`-tagged) node, every import: `started-at`, `completed-at`, `duration-seconds`,
`activity`, `raw-activity` (only when `activity` mapped to `"other"`), `source`
(`"healthkit"`/`"synthetic"`), `source-workout-id`, `energy-kilocalories`?, `average-heart-rate`?,
`maximum-heart-rate`?.

Root, strength-only roll-ups: `exercise-count`, `set-count`, `total-volume-kilograms` (computed
server-side, `Σ repetitions × loadKilograms` across every set — never trusted from the client).

Root, cardio-only roll-ups: `split-count`, `distance-meters`?, `elevation-meters`?,
`average-speed-meters-per-second`?, `average-pace-seconds-per-kilometre`?.

Exercise node: `ordinal`, `exercise-set-count`, `exercise-volume-kilograms`.
Set node: `ordinal`, `repetitions`, `load-kilograms`, `volume-kilograms`, `rpe`?,
`set-completed-at`?.
Split node: `ordinal`, `split-distance-meters`, `split-duration-seconds`,
`pace-seconds-per-kilometre`? (computed only when distance > 0), `average-heart-rate`?,
`energy-kilocalories`?.

(Exercise/set/split-node predicates are namespaced — `exercise-set-count` not `set-count`,
`split-distance-meters` not `distance-meters` — deliberately distinct from the root node's own
roll-up predicates of similar name, since `graph_facts` has no per-tag predicate namespacing of
its own: two different predicate strings on two different nodes never collide, but reusing the
exact same string for a per-node value and a workspace-wide-looking roll-up on the SAME node kind would
be a real ambiguity source for a future `runView`/search consumer.)

### 1.4 "No new mechanism" — the graph is built entirely from Phase 1's existing primitives

Every node/tag/fact/edge write `WorkoutsService.importWorkout` performs
(`packages/backend/src/workouts-service-live.ts`) goes through the **same** primitives every other
mutation in this codebase already uses:

- Node creation mirrors `workspace-durable-object.ts#createNode`'s own inline dance
  (`NodesRepository.put` + `upsertNode`/`indexNodeText` read-model sync + `syncFeed.append`) —
  there is no workout-specific node table.
- Tag assignment, fact writes, and edge creation call `GraphService.assignTag`/`.addFact`/
  `.createEdge` directly — the exact same methods `createTag`/`addFact`/`createEdge`/`assignTag`
  RPCs already exposed in Phase 1. `WorkoutsService` adds ZERO new storage collections for graph
  data (the one new collection, `workoutImportReceipts`, is idempotency bookkeeping — see §2.3 —
  not graph data).

This is what "proves graph generality" concretely means: a fifth, unrelated domain (fitness) is
representable as Node+Tag+Fact+Edge with no schema change, no new SQL table, no new sync-feed
entity kind beyond a plain string tag, and no new authorization primitive beyond the one
`requireRoleForGovernedWorkspace` gate every other mutation already uses.

### 1.5 One atomic `importWorkout` RPC, not N generic graph calls — and why that's still "no new mechanism"

A single strength session (2 exercises × ~3 sets) is already ~15 node/tag/fact/edge writes; a
real HealthKit history import could be dozens of workouts. `packages/domain/src/workout-rpc.ts`
adds exactly two new RPC methods — `importWorkout` (atomic, idempotent, `"build"`-gated) and
`listWorkoutImports` (`"use"`-gated) — for three reasons spelled out in that file's own doc
comment: (1) atomicity (a dropped connection mid-import must not leave a half-built subgraph — see
§2.4 for how this is actually enforced), (2) round-trip cost (one call instead of dozens), and (3)
a single place to compute a real, server-side, non-client-trusted idempotency hash (§2.3). The
RPC's *implementation* still only calls the Phase 1 primitives above — it is a batching/atomicity
convenience at the wire boundary, not a second way to create graph data, which is why this doesn't
contradict §1.4.

Both new methods are gated exactly like every other governed-workspace RPC method
(`workspace-durable-object.ts#importWorkout`/`#listWorkoutImports`, both call
`requireRoleForGovernedWorkspace` — no exceptions, per this codebase's own hard-won discipline after
two prior real gaps, Phase 4 and Phase 5). Proven for real:
`packages/backend/test/workouts.test.ts#"rejects an anonymous caller on a GOVERNED workspace"`.

### 1.6 Observer-exclusion convention, applied to `WorkoutImportReceipt.rootNodeId`

The hard constraint asks that any `linkedNodeId`-style field pointing at a node respect the same
observer-exclusion pattern `CalendarService#hiddenCalendarDerivedNodeIds` established for
`Meeting.linkedNodeId`/`Bookmark.linkedNodeId`, even though nothing hides workout nodes today.
Workouts themselves have no such field (a Workout *is* a node, not a row referencing one — §1.4),
but the new `workoutImportReceipts` collection's `rootNodeId` (§2.3) is exactly that shape: a
non-graph row that references a node.

`workspace-durable-object.ts#listWorkoutImports` computes `hidden = calendar
.hiddenCalendarDerivedNodeIds(workspaceId, currentUser?.email)` — the identical call
`listNodes`/`getNode`/`getMeeting`/`listMeetings` already make — and applies it via
`filterHiddenWorkoutImportReceipts`. This is a **row-level filter**, not the field-level
`sanitizeMeetingLinkedNodeId`/`sanitizeBookmarkLinkedNodeId` omission those two entities use — a
deliberate, documented variant (`workspace-durable-object.ts`, `filterHiddenWorkoutImportReceipts`'s
own doc comment): `Meeting.linkedNodeId`/`Bookmark.linkedNodeId` are *optional* annotations on an
otherwise-independent entity, so hiding just the field and keeping the row is correct; a
`WorkoutImportReceipt.rootNodeId` is mandatory — a receipt with no node reference isn't a
degraded-but-valid receipt, it's meaningless — so the whole row is dropped instead, the same
"omit, never emit a semantically-broken shape" discipline `listNodes`'s own row-filtering already
uses for hidden nodes themselves.

## 2. The testable HealthKit abstraction

### 2.1 `WorkoutDataSource` — the real dependency-injection seam

`native/AthenaeumCore/Sources/AthenaeumCore/Workouts/WorkoutDataSource.swift`, same
domain/implementation split `AudioCaptureSource.swift` (Meetings, Phase 6) already established for
the identical reason:

```swift
public protocol WorkoutDataSource: Sendable {
    func requestAuthorizationIfNeeded() async throws -> Bool
    func fetchRecentWorkouts(since: Date, limit: Int) async throws -> [ImportedWorkout]
}
```

`ImportedWorkout` (same file) is the source-agnostic value type both implementations below
produce — `sourceWorkoutId`/`source`/`activity`/`rawActivity`/`startedAt`/`completedAt`/
`durationSeconds`/`energyKilocalories`/`averageHeartRate`/`maximumHeartRate`, plus an **optional**
`strengthExercises: [ImportedStrengthExercise]?` and a `cardioSplits`/`cardioTotals` pair. See its
own doc comment for why `strengthExercises` is optional and separate from the cardio fields rather
than one payload enum mirroring the wire shape directly — summary: what a *data source* can
observe (HealthKit: never per-set structure) and what the *wire payload* requires (workout-rpc.ts:
strength needs ≥1 real exercise) are different concerns, resolved by `WorkoutImportBridge` (§2.4),
not baked into this value type.

### 2.2 `HealthKitWorkoutDataSource` — real, genuinely compiles, genuinely untested live

`native/AthenaeumCore/Sources/AthenaeumCore/Workouts/HealthKitWorkoutDataSource.swift`. Real
`HKHealthStore`/`HKSampleQuery`/`HKStatisticsQuery`/`HKQuery.predicateForObjects(from:)` usage —
not stubbed, not simulated. Verified **this stage**, against the real HealthKit SDK headers on
this machine (`/Applications/Xcode.app/.../SDKs/MacOSX27.0.sdk/System/Library/Frameworks/
HealthKit.framework/Headers`), before writing the class, not assumed from memory:

- `HKWorkout.totalEnergyBurned`/`.totalDistance` are `API_DEPRECATED` (macOS 15+, in favor of
  `statistics(for:)`/`allStatistics`) in this SDK's own headers — this class uses
  `HKStatisticsQuery`/`statistics(for:)` throughout, never the deprecated properties, since this
  is new code with no legacy-API obligation.
- Average/maximum heart rate are NOT carried on `HKWorkout` directly — derived via a separate
  `HKStatisticsQuery` over `HKQuantityType(.heartRate)`, correlated to the workout via
  `HKQuery.predicateForObjects(from: workout)` (Apple's documented pattern).
- **Per-exercise/per-set structure for a `.strengthTraining` `HKWorkout` is not exposed by any
  public HealthKit read API** — confirmed by inspecting `HKWorkout.h`/`HKWorkoutActivity.h`
  directly: `workoutActivities`/`allStatistics` describe aggregate statistics per constituent
  *activity* (for multi-sport workouts), never per-exercise-name/per-set/per-rep data, which lives
  only inside whichever app recorded the workout and is never re-exposed to other apps. This class
  therefore **always** returns `strengthExercises: nil`, unconditionally, for every real read —
  not a gap to fill later, a real platform ceiling.
- Cardio **splits** are derived best-effort from `HKWorkoutEvent`s of type `.lap`/`.segment`
  (their only guaranteed field is a `dateInterval`; a per-segment `HKStatisticsQuery` bounded to
  that interval recovers the segment's own distance/heart-rate/energy). Many real workouts carry
  no lap/segment events at all (an originating-app choice) — `cardioSplits` is empty in that case,
  root-level `cardioTotals` still populate from the whole-workout statistics query.

against the real HealthKit SDK (swift build)"):

**Genuinely untested live**, for the exact reasons `ScreenCaptureKitAudioSource`'s own header

### 2.3 `SyntheticWorkoutDataSource` — the real test double, proven through the real pipeline

`native/AthenaeumCore/Sources/AthenaeumCore/Workouts/SyntheticWorkoutDataSource.swift`. Two
realistic fixtures, per the hard constraint's own examples:

- `strengthFixture` — Back Squat (3 sets, ramping weight, last set to RPE 8) then Bench Press
  (2 sets): "a strength session with multiple exercises/sets."
- `cardioFixture` — a 3 km run with three real 1 km splits, distance/pace roll-ups populated: "a
  cardio session with distance/pace."

`fetchRecentWorkouts(since:limit:)` filters/sorts/limits exactly like a real HealthKit date
predicate + sort descriptor would (`SyntheticWorkoutDataSourceTests#testFetchRecentWorkouts...`).

**The idempotency mechanism this stage adds, backend side** (needed for the real pipeline to be
genuinely re-runnable, matching Enchiridion's own `workout_import_receipts` precedent almost
verbatim): `packages/backend/src/workout-collections.ts`'s `workoutImportReceipts` collection,
keyed by a real `UniqueIndex` on `sourceWorkoutId` — `WorkoutsService.importWorkout`
(`workouts-service-live.ts`) computes a server-side SHA-256 hash of the decoded input's own
content (`crypto.subtle.digest`, never trusted from the client — same discipline this codebase's
HMAC'd share keys/OAuth state already use) and, on a repeat `sourceWorkoutId`: returns the
existing receipt unchanged (`duplicate: true`) if the hash matches, or fails closed with
`ValidationError` if it doesn't (a genuine content conflict — same-id-different-content is treated
as a caller bug, never silently overwritten or silently ignored).

### 2.4 `WorkoutImportBridge` — the transformation pipeline, and the strength-fallback decision

`native/AthenaeumCore/Sources/AthenaeumCore/Workouts/WorkoutImportBridge.swift` — pure
`ImportedWorkout → RPCWorkoutImportPayload` transformation (`payload(for:)`, no I/O, unit-tested
in isolation — `WorkoutImportBridgeTests`) plus the actual RPC call
(`importWorkout(_:using:)`, `native/AthenaeumRPC/Sources/AthenaeumRPC/
WorkspaceRPCClient+Workouts.swift`).

**The fallback decision this stage had to make for real** (not hypothetical — this is what a real
`HealthKitWorkoutDataSource` read of a `.traditionalStrengthTraining` workout ALWAYS produces,
§2.2): `workout-rpc.ts`'s wire schema requires a `.strength` payload's `exercises` array to be
non-empty (`Schema.minItems(1)`) — a strength-activity `HKWorkout` with `strengthExercises == nil`
cannot be sent as `.strength(exercises: [])`. `payload(for:)`'s rule: if `strengthExercises` is
`nil` or empty, send `.cardio(splits: [])` instead — an empty-but-schema-valid cardio payload. The
resulting root node ends up tagged `Cardio Workout`, not `Strength Workout`, even though its own
`activity`/`source-workout-id` facts still correctly say `"strength-training"` — a deliberate,
documented trade-off (`WorkoutImportBridge`'s own header comment names and rejects the
alternative: a workout typed as neither Strength nor Cardio would weaken the tag-closure guarantee
every other Workout-tagged node gets). Proven:
`WorkoutImportBridgeTests#testStrengthActivityWithNoStructuredDataFallsBackToEmptyCardioPayload`
and `#testEmptyStrengthExercisesArrayAlsoFallsBackToCardio`.

`AthenaeumRPC`'s own layering constraint mattered here: `WorkspaceRPCClient+Workouts.swift` lives in
`AthenaeumRPC` (which must stay watchOS-buildable, per that package's own header comment, and
therefore cannot depend on `AthenaeumCore`/HealthKit at all) and defines only plain, source-
agnostic wire types (`RPCWorkoutImportPayload` etc.); `WorkoutImportBridge` — the piece that
actually knows about `ImportedWorkout`/HealthKit-flavored types — lives in `AthenaeumCore`, which
already depends on `AthenaeumRPC`. The dependency arrow only ever points one way.

## What was and wasn't verified live — summary

**Verified live, this stage:**
- `HealthKitWorkoutDataSource.swift` compiles against the real HealthKit SDK
  (`swift build`, `native/AthenaeumCore`) — confirmed the exact API shapes used
  (`HKStatisticsQuery`, `HKQuery.predicateForObjects(from:)`, `statistics(for:)` vs. the
  deprecated `totalEnergyBurned`/`totalDistance`) by reading the real SDK headers first, not from
  memory.
- The full synthetic-source → transformation → RPC → backend → graph pipeline, against a real
  running `wrangler dev` backend (§2.5 transcript above) — 3 native tests + 8 backend tests, all
  passing.
- `SyntheticWorkoutDataSource`'s and `WorkoutImportBridge`'s pure logic — 10 additional unit tests
  (`SyntheticWorkoutDataSourceTests`, `WorkoutImportBridgeTests`), no network.
- Domain-schema round trips and tag/relation-definition invariants — 17 tests
  (`packages/domain/src/workout.test.ts`).
- Full regression: `packages/domain` (518 tests) and `packages/backend` (193 tests) both green
  after this stage's changes; `native/AthenaeumCore` (69 tests, 3 newly-live via the transcript
  above) and `native/AthenaeumRPC` (20 tests) both green.

**NOT verified, and cannot be verified in this environment (stated explicitly, per the hard
constraint):**
- `HealthKitWorkoutDataSource` has never executed against a real `HKHealthStore` — no TCC consent
  dialog can be clicked by a human here, and this machine has no real Apple Watch/HealthKit data
  regardless of authorization. Every code path inside `requestAuthorizationIfNeeded`/
  `fetchRecentWorkouts`/the per-workout `HKStatisticsQuery` helpers is real, type-checked Swift
  that has never actually run.
- Whether `HKWorkoutEvent`-derived splits (`cardioSplits(for:distanceType:)`) look sensible against
  a REAL multi-lap running workout is unverified — the logic is real and the query shapes are
  correct per the SDK headers, but no real lap-marked `HKWorkout` exists here to run it against.
- Real-device behavioral edge cases HealthKit is known for (a workout with a `nil`
  `HKWorkoutActivityType` mapping outside this file's `mapActivityType` switch, a workout whose
  `energyKilocalories`/`distance` statistics are genuinely absent because the recording device
  never wrote them, authorization silently downgrading a query to zero results per HealthKit's own
  privacy-preserving read-authorization opacity) are handled defensively in code (optional
  everywhere HealthKit itself makes a value optional, `.other` + `rawActivity` fallback for
  unmapped types) but not exercised against real data.
- Whether `HealthKitWorkoutDataSource`'s macOS 13.0 availability floor (matching this SDK's own
  `API_AVAILABLE(..., macos(13.0))` annotations on `HKHealthStore`/`HKSampleQuery`) holds on an
  actual shipping macOS release is unverified — this environment's SDK reports as `macosx27.0`, a
  build identifier ahead of any publicly shipping macOS at the time of writing; the annotations
  were read directly from headers on this machine, not cross-checked against a real device.
