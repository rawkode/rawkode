# Transitional Workspace Ledger

Transcript segment appends now use the same ledger boundary: meeting and generated segment
identities are public side effects, while transcript text, rationale, attribution, and the strict
speaker-presence marker remain in the private command payload. Meeting lifecycle and calendar
ingestion are still direct migration slices.

The public `defineTagField`, `createRelationDefinition`, `createBookmark`, `startMeeting`, `appendTranscriptSegment`, and `syncNoteReferences` mutations are now ledger-governed alongside
the graph and Supertag membership mutations listed below; their schema/mention projections, sync-feed
entries, commands, receipts, events, and outbox intents commit atomically with replay protection.

`WorkspaceDurableObject.createNode`, the P5.2 `decideAgentChangeProposal` boundary, the reviewed chat decision boundary (`decideChatReview`), and the graph mutations `addFact`, `createEdge`, `createTag`, `syncNoteReferences`, `assignTag`, and `unassignTag` are the public mutations currently routed through the workspace-local ledger. The legacy `mergeChanges` and `revertChanges` RPCs remain source-compatible adapters, but their actual promotion/reversion now enters the same reviewed decision transaction with a bounded compatibility rationale, a server-generated request identity, chat custody, and a v2 replay receipt; any non-empty compatibility write requires an authenticated caller. `createNode` derives principal (`authenticated email` or canonical `anonymous`), build capability and governed/ungoverned policy on the server after the existing role gate. Proposal decisions require an authenticated principal, caller-supplied rationale and evidence provenance; the proposal snapshot is re-read and compared byte-for-byte before any promotion or rejection. A stale or missing target becomes a durable `conflicted` decision with no partial write. Reviewed chat decisions additionally bind a structured witness, range mode, pending-App count, and an exact pending-App/code-version witness to the command, then recompute all guards inside the mutation transaction. The graph mutations require a logical request ID, typed asserted attribution, and caller commit message; the latter two are retained in private typed command payloads while public activity uses deterministic server-derived messages. Tag membership mutations return `changed: false` for idempotent no-ops, still persist an authenticated command and typed replay receipt, and emit no duplicate read-model, feed, event, or outbox transition. Mention reconciliation canonicalizes the complete desired set once, journals created edges and pre-delete tombstones, and records no event/outbox for a no-op. Their graph/feed/command/event/outbox writes execute in one caller-owned synchronous DO transaction. All paths use `athenaeum.workspace-ledger.v1`; the `create-node-title-compat.v1` message remains a deterministic server-derived compatibility placeholder because that public caller supplies no rationale, while the newer graph commands use versioned operation labels. It is not a claim about caller intent. A future full command contract must require caller/job rationale for every mutation; explicit-ID replay remains immutable and deterministic under the compatibility derivation.

App create, code update, and delete are now ledgered too. They require an authenticated human UI actor, stable app ID (for create), request ID, canonical commit message, and asserted UI surface. Code saves bind the exact literal UTF-8 byte digest and byte length plus the loaded code pointer and `updatedAt`; deletes bind the loaded revision and both code pointers. Private command payloads and receipts retain only the App/code identity and exact source digest/length needed for audit and replay; public activity omits those identifiers and all source, while event/outbox projections carry only the safe App identity/version needed for downstream routing. A replay reconstructs the public code result only after reading and verifying the precise stored code version.

App row revisions are explicit monotonic counters rather than timestamp fences: every persisted
row transition increments `revision`, and `acceptedRevision` records the last accepted lineage.
Rows written before these fields existed are read through a conservative compatibility migration
that seeds both counters at `1`; it never infers “never accepted” from timestamps, so an ambiguous
legacy pending row is retained rather than deleted on revert. During the cutover, an in-flight
proposal with an intact legacy App snapshot may proceed only when its migrated bytes match the
current row exactly; any other snapshot drift conflicts durably. New writes persist the counters,
which makes the migration self-healing without treating historical timestamps as authority.

An explicit client node ID supplies the compatible cross-call replay identity for `createNode`; the other ledgered graph and workforce-boundary mutations use caller-generated request IDs and namespaced request identities. Calls without a stable identity receive a fresh outer-RPC identity and are not represented as cross-client retries. Commands are validated against the exported `LedgerCommand` Effect Schema before insertion; the relevant KV projection, SQL/FTS read model, sync-feed entry, outbox intent and receipt are written inside one synchronous DO-storage transaction. P5.2 adds a durable decision event and outbox intent alongside the accepted/rejected/conflicted receipt, with request identity and fingerprint replay protection. The routing inventory catalogues every public Workspace mutation RPC (including `mintAppRunCredential`) plus the App HTTP mutation path; the ledger set is explicit and all remaining routes are direct bypasses until they receive compatible command contracts. This is still not an authority-complete ledger: direct entity writes, chat tool execution, sync imports, calendar/meeting ingestion, app/workflow execution, and workforce execution remain later migration slices.
